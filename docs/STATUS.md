# neuron: state of the project

## the quick version

- **Windows beta:** this is the release you can download today. i use it instead of Synapse on my Naga V2 Pro and BlackWidow Chroma V2.
- **Other Razer devices:** not all verified. identification, successful reads and actual working controls are different things.
- **Beyond Razer:** a PowerA gamepad has been tested for input and rumble on Windows. Logitech HID++ discovery is experimental and read-only, without hardware verification.
- **Linux:** the app and CLI build from source, but no Linux package or native Razer HID test yet. **macOS:** no backend yet.
- **Got different hardware?** [share what works](https://github.com/worflor/neuron/issues/new?template=device_report.yml), or [collect evidence yourself](reference/COMPATIBILITY-LAB.md#try-it-yourself).

This page tracks [v0.1.7](https://github.com/worflor/neuron/releases/tag/v0.1.7), published 2026-11-08. Windows and Linux CI passed, the release's checksums and provenance attestations were verified, and it scanned clean with Microsoft Defender. These are build checks, not proof that a new device works.

The Compatibility Lab was checked against 30 HID collections across six Windows device groups and an unrelated ITE device (`0b05:1866`). This verifies descriptor inventory and reviewable export, not device command support. Passive input capture and Linux hardware collection still need physical testing. [How the Lab works](reference/COMPATIBILITY-LAB.md).

Lighting scene changes now dissolve through the persistent base renderer. Software regressions cover interrupted edits, renderer state and local/host parity; live LED fades have been checked on the owner's Windows setup. Other hardware and game coexistence still need verification.

The table below grades what actually works. [The README](../README.md#honesty-proven-gated-absent) has the device-write ledger.

| grade | meaning |
|---|---|
| 🟢 solid | Daily-driven or directly tested on the named hardware. |
| 🟡 works, polishing | Usable, with recent changes or rough edges still being exercised. |
| 🟠 under-tested or partial | Implemented in part or not yet exercised enough to rely on broadly. |
| ⚪ planned | No working implementation yet. |

A row's grade changes only with evidence: name the hardware, the platform and the date, and
say what is still unverified. Mock and software-renderer results are recorded as such and never
raise a grade on their own. What changed in each release is in [`CHANGELOG.md`](../CHANGELOG.md).

## Feature status

| area | grade | evidence and limits |
|---|---|---|
| Device control | 🟡 works, polishing | DPI, polling, brightness, battery, scroll-stage selection and other reads are used on a Naga V2 Pro and BlackWidow Chroma V2. DPI, polling, brightness and scroll-stage setters require matching read-back; the scroll-stage cycle reads the device's own stage and enabled count (`15/80`, `15/81`, verified live 2026-09-29). The legacy BlackWidow brightness getter and write/read round-trip were checked on the attached board. Receive-frame validation passed mocks and read-only BlackWidow and awake Naga getters. |
| Naga side plates | 🟢 solid | The mouse reports plate swaps; Neuron debounces them and scopes binds to the seated plate. Detaching clears that layer. |
| Trigger → action dispatch | 🟢 solid | Binds, HyperShift layers and app-focus rules use one tested engine. |
| Keyboard Fn layer | 🟡 works, polishing | Driver mode hands Fn to the host, so Neuron re-creates it. On the BlackWidow Chroma V2, Fn+F2/F3 were verified live on 2026-11-08. Its row comes from the definition, and Fn+F10 toggles the firmware game mode. Media-key reports from V3/V4-class boards map to media keys, unverified on hardware. Synthesized keyboards get no Fn F-row; F9, F11 and F12 keep their plain key. |
| Clipboard transforms, pockets, history and screenshots | 🟠 under-tested | Typed ordered text transforms can include one stored Python macro that receives the current intermediate text as `ctx.clipboard` and must return a string; macro-backed transforms run asynchronously behind the arm gate and use the clipboard sequence check before commit. Bounded regex previews, full-format named pockets, in-session displaced-state history, and screen/window/region screenshot actions are implemented. On Windows, native text transforms, four-format Pocket/history restore, image Pocket restore, window PNG/clipboard capture and region cancellation were exercised on 2026-10-01. Macro-backed transform behavior, region drag capture and broader application-format compatibility remain unverified. Headless CLI/daemon screen and window captures report completion to stderr; region selection requires the resident app. Durable pockets are capped at 128 MiB, history at 20 items / 16 MiB, transforms at 1 MiB of text, and explicit CLI body inspection at 16 MiB. |
| Lighting-layer, dial scroll, Undo | 🟠 under-tested | Typed layer mutations validate before the app persists and restreams the selected stack. Dial keeps output/mic compatibility and adds hover/hold-anchored Windows scrolling. The 20-entry session journal uses successful audio/profile receipts and app lighting receipts; the headless daemon has no compositor target. Automatic app-focus switches and first activation from an empty profile cursor are not undoable. The Windows inline layer editor and direct/nested output-gain Undo were exercised on 2026-10-01. Physical layer output, anchored window scrolling and microphone-gain Undo remain unverified. |
| Controllers and any HID device | 🟠 under-tested | Windows only. Buttons, sticks, triggers and hats come from each device's own report descriptor, and a stream whose buttons contradict its descriptor is caught and feeds neither binds nor the radial ([how it works](GDD.md#controllers-and-anything-else-with-buttons)). Pads GameInput delivers come through it and Raw Input's copy of the same pad is dropped; everything else comes through Raw Input, and a descriptor-less stream through a layout file (Switch Pro, from SDL's zlib driver). Only GameInput and layout pads share the standard-pad button names; a Raw Input pad's buttons are its descriptor's own numbers. A pad unplugged mid-press releases what it held. A held cast trigger plus a pushed stick aims the radial, and the aiming pad renders the wheel as a knob (`knob.rs`; PAD FEEL on the radial sets its strength from off to 150%, "feel it" plays the phrase on the pad in hand). Rumble is built from a Game Pad collection's declared HID Physical Interface Device outputs: the XInput-HID shadow every Xbox-protocol pad gets is verified (all four motors of a PowerA pad, at any strength, 2026-09-30; `neuron rumble --tour`), other pads' motors carry no declared roles and stay behind `NEURON_HAPTICS_WRITE`, and joystick and wheel force feedback is never written. GameInput's unit id is opaque, so rumble refuses two connected pads with the same VID:PID rather than guessing which shadow belongs to which pad. A pad cast trigger uses sticks matching its canonical PID; identical physical pads share that id, so the selected path is latched only once aiming engages and a disconnect cancels the cast. Battery and motion from GameInput, and any non-control value a HID descriptor declares, feed a sensor registry (`neuron pads`). Verified 2026-09-30 on a PowerA pad: background reading, no events at rest, binds fire, the stick aims and fires the radial, the knob's feel. Not yet exercised: the unplug release, Bluetooth pads, two identical pads (identity is the USB pid alone, so they share one), the Switch Pro stream (its start-up answers but stays gated, `NEURON_PAD_INIT`), Linux and macOS sources. |
| Firmware-performed binds | 🟠 under-tested | On a device with firmware button functions (Naga V2 Pro thumb grid), a key bind is written into the mouse and other binds ride a private F-key the hook swallows, handed out from F24 down and never shared between devices; a software-injected F-key (a hotkey tool) is never taken as one, but a physical macro pad sending the same F-key while it is assigned would be. The Naga is kept in normal mode, where those functions run. Verified live 2026-09-30 on the 12-button plate over the cable (a firmware `g`, a host scroll-stage cycle, factory restore on exit). A button two plates bind differently is planned for the seated plate, re-planned when the plate changes (unit-tested; not yet verified live). Not yet exercised: the dongle link, sleep/wake re-apply, the 6-button plate, press-to-bind capture of a bound key. |
| Host-side device binds | 🟡 works, polishing | For a key a device's firmware cannot perform, the keyboard hook decides which device sent it: a key only one connected device can send (a definition's buttons limit a mouse to its own keys) is exact, and a key several keyboards share goes to the one typed on last. Verified live 2026-11-08 (BlackWidow F8 bound to `g`). The first press after switching between two full keyboards can be misattributed. |
| Arm gate | 🟢 solid | The process starts disarmed, then a normal Windows GUI launch arms input when live dispatch starts so tray remaps work after logon and Windows crash recovery. `--safe` stays disarmed. Tests cannot arm input; device writes and synthesized input have separate controls. If a device's button functions cannot be verified (a sleeping wireless mouse), an armed stance shows "arming", retries every 5 s and arms once every device verifies stock. |
| Audio control | 🟢 solid | Mute, gain and output switching use the OS mixer. Also tested with the BlackShark V2 and its included USB sound card, and the Seiren V3 Mini; these have no extra device-specific Neuron controls. |
| Synapse import, purge and discover | 🟢 solid | Plaintext export import, Windows purge and device discovery are implemented. Encrypted Synapse cloud profiles are not supported; a Synapse 3 layout is read instead from the mapping log its service writes, which holds only what the last Synapse session set (keys and mouse buttons; macros, modifier chords and DKM-addressed buttons are reported, not imported). |
| Notifications | 🟢 solid | Visual cards and optional audio confirm committed changes. |
| Profiles | 🟡 works, polishing | Capture, apply, rename and app-based switching are implemented. A profile groups settings, lighting and binds; lifecycle edge cases are fixed and need continued use. |
| Device adoption | 🟡 works, polishing | Capability probing synthesizes definitions for unfamiliar `razer_report` devices and direct-attached Logitech HID++ devices. The Naga V2 Pro and BlackWidow Chroma V2 are hardware-verified; HID++ adoption is read-only and has no hardware verification. Device files load only within the commands Neuron's protocol knowledge gives each name. |
| Lighting | 🟡 works, polishing | Firmware effects, per-key frames, pattern × spectrum layers, and live data layers are implemented ([GDD](GDD.md#lighting)). Wildlife and Tidepool (handcrafted stateful patterns) have not been visually checked on real hardware. Gradient presets and per-effect pairing chips were checked in the running app, and a software-renderer test draws the page and hovers a chip; not checked on other hardware. Layer editing and data feeds need more everyday use. The second colour picker and its suggestions are opt-in from the spectrum header; they were exercised end to end in a software-renderer test and looked at in its frames, not yet used day to day. Suggestions come from fixed rules. Luma-T (Luma core v4.4 with taste head v6) ships built in, and a learned colour model (core v4.1 to v4.4) in the run root replaces it: the port matches the reference implementation on 254 recorded requests across its four tasks for a small test model and, run by hand, on the gradient requests published with the trained v4.2, v4.3 and v4.4. A taste head (`colour-taste.lumataste`, beside the core) can choose among the model's readings: the port matches Luma's reference on every stage (readings, tokens, scores, a person's term, the decision) for a small test head on 141 requests and, run by hand, for the trained heads v5 and v6 on 47 each. With the pick journal on, a person's own taste is fitted from what they take and dismiss once three slates are decided. The model and head are research assets: by Luma's study the stack is right about two times in three when it speaks and weakest on companion edits; none of it has been judged in use here, and a request with the head takes about 0.15 s off the UI thread on the trained bundles. Its doubts (squiggles on the strip) and its terrain (rings in the plane, a skyline on the rail) were looked at in software-renderer frames with the trained model on one palette; whether they help has not been judged in use. Answers are computed off the UI thread; that path, the keyboard control of the picker and the pick journal (off by default) have not been exercised in the running app, only the same logic run inline in the test. |
| Charging / battery colours | ⚪ planned | Battery telemetry and the Vitals lighting layer exist; charging-override control is not implemented. Reuse the compositor and typed, device-agnostic charge-state policy; keep protocol differences in device definitions and explicitly associate each dock with its source mouse. Intended controls: retain normal lighting, custom battery colours, and steady/off/resume when full. [OpenRazer's mouse override](https://github.com/openrazer/openrazer/blob/477f4d6d3ab7e9deb6310d5bd3742560c5cbe80d/driver/razermouse_driver.c#L1803) is a research lead, not proof for every mouse or dock. Awaiting identification and testing of the owner's older Razer mouse/dock, if available. Verify mouse and dock separately, including undock, reconnect and PC sleep; firmware persistence is unknown. Writes require owner approval, protocol-ledger evidence and applicable gates/read-back. |
| Macros and beacons | 🟡 works, polishing | BOUND and RAW CPython workers start on demand and then stay warm. Ask/notify, persistent state, macro composition and a source-preserving block editor are implemented. [The API reference](reference/MACROS.md) covers every helper; long-run ergonomics need work. BOUND runs behind a runtime wall that refuses file, process, network and native access; RAW Python is unsandboxed. |
| Main GUI | 🟡 works, polishing | The Slint window defaults to FemtoVG/OpenGL. The software UI renderer is compiled in and can be forced with `NEURON_RENDERER=software`. The opt-in WGPU UI renderer builds, but measured idle CPU and memory were higher on the development machine; it does not accelerate overlays or material shading. Windows overlay instruments still compose pixels on the CPU. |
| Reliability and recovery | 🟡 works, polishing | Flight recorder, crash log and read-only diagnostics are wired. Windows auto-relaunch is implemented but has not been exercised by a real crash or hang. |
| Onboard memory | 🟠 partial | Storage accounting and volatile writes work. Full onboard profile-slot persistence and scroll feel-curves are not complete. |
| Spellweaving at scale | 🟠 under-tested | Gesture recognition and radial dispatch work. Large glyph vaults and fully populated radial menus need sustained use. |
| Instruments | 🟠 uneven | Teleport, tether, whiteboard, glance, window actions, dial, knockback and control are present at different maturity levels. The whiteboard cannot save ink to disk yet. |
| CLI and headless daemon | 🟠 under-tested | The installed Windows CLI has driven real hardware and shares the GUI's core engine. Its broad command surface and daemon path have had less day-to-day use. |
| Protocol host | 🟠 early | Loopback Chroma REST and OpenRGB reach the lighting arbiter. Native Chroma shared memory uses the packaged protected section broker with the regular tray at Limited integrity. A synthetic named-mapping test replays a captured game frame through the production snapshot and decode paths, and the final installed build received live native Chroma traffic from a real game. Client counts are bounded. A Chroma lab under LIGHTING → VISITORS splits the connected game's own keyboard frames into an ambient colour, held key colours, animated keys and recurring effects with stable ids; that grouping is regression-tested against 750 frames of real Overwatch play and has been tuned on that one game only. Effect ids, names and hidden flags persist per game exe. From the lab an effect can be hidden (the keyboard holds the at-rest picture from the early guess, about 0.25 s in), and a lens can restyle all game paint (hue, saturation, brightness). An effect can also be bound to a feedback action through a game-light trigger on the one dispatch engine, which refuses any rule that would press keys, click, run a macro or a command. A Game Light data layer carries the game's ambient and effect colours to any device. The frame codec reads each device class (keyboard, mouse, headset, mousepad, keypad, room lights) at its own record layout, checked against a live Overwatch capture and an independent open-source reader. It decodes custom grids, per-key overrides and static colours, and renders the SDK's parametric effects (wave, spectrum, breathing, blinking) rather than reading them as colour; a suspended game reads as suspended. The lab keeps the resting pictures a game returns to as named scenes. A scene can notify when it ends while the game isn't focused, and can bind a feedback action to its start. A capture saves as both the fixture stream and a `.chroma` animation in the SDK's file layout; no Razer tool has opened one yet. Against a running Overwatch, the lab showed the mouse, headset, mousepad and room grids, recognised a saved scene under the same id after a restart, and saved a scene's name, alert flag and bound action. A scene alert firing, a bound action running, hiding, the lens and the Game Light layer have not been exercised live in a match; the lab's live tap has no automated tests. The non-keyboard layouts are verified only on static frames, and parametric effects only on synthetic records. Broader game compatibility remains planned. |
| Momentary mic | 🟠 under-tested | Press holds mute and release restores it. Config swaps, worker respawn and exit release held state; the path has had limited real-world use. |
| Install and update | 🟡 works, polishing | The current Windows package was installed from a clean application state, updated over a running tray, reapplied through the portable updater, and cleanly uninstalled on the development machine. Installed file hashes matched staging; uninstall removed the binaries, startup tasks and protected broker while preserving generated user configuration. Setup provisions or refreshes the protected Chroma broker after UAC approval and migrates the historical elevated tray task to a limited task; the standalone updater refuses that unsafe historical task before changing files. The machine-wide broker and startup task support one owning Windows user. This is not a separate clean-machine run. Linux update logic has synthetic install, rollback and checksum tests, but no released Linux package or native installation run. |
| Linux HID | 🟠 hardware-unverified | The hidraw transport builds and passes local tests under WSL2. No Razer device has exercised its feature-report path on Linux. |
| Linux GUI | 🟠 partial | The source builds a Slint window with device settings, lighting editor, GTK tray and best-effort hotkeys. Live input, audio and overlay work is on [`codex/linux-runtime-parity`](https://github.com/worflor/neuron/tree/codex/linux-runtime-parity). Its overlay does not yet match Windows, and its input path needs a native desktop and hardware run. No Linux download is published yet. |
| macOS | ⚪ planned | No backend or release build. |

For device-write evidence and feature gates, see the [README ledger](../README.md#honesty-proven-gated-absent). If a feature marked solid breaks, please [report the device and steps to reproduce](https://github.com/worflor/neuron/issues).

## Current engineering checks

v0.1.7 (2026-11-08): `./validate.ps1 -Mode full -Locked` passed in the release workflow on Windows,
and the Linux CI job passed on the tagged commit. The release was installed over v0.1.5 on the
owner's Windows 11 machine on 2026-11-08 through real UAC: the Chroma broker was replaced and
Microsoft Defender raised nothing. v0.1.7 also carries the unpublished v0.1.6, which stayed a
draft after Defender flagged its broker during installation testing.

Not yet verified: setup, update and uninstall in a clean Windows VM; native Chroma games after a
broker update; Linux on real Razer hardware; the BlackWidow V3 and V4 X keyboard lighting.
