# neuron: state of the project

v0.1.1 is the current public Windows beta; the working tree is the proposed v0.1.2, still beta mk1. This page tracks what has been exercised on hardware, what is implemented but needs more use, and what is still planned. The [README](../README.md) has the device-write ledger.

| grade | meaning |
|---|---|
| 🟢 solid | Daily-driven or directly tested on the named hardware. |
| 🟡 works, polishing | Usable, with recent changes or rough edges still being exercised. |
| 🟠 under-tested or partial | Implemented in part or not yet exercised enough to rely on broadly. |
| ⚪ planned | No working implementation yet. |

## Feature status

| area | grade | evidence and limits |
|---|---|---|
| Device control | 🟡 works, polishing | DPI, polling, brightness, battery, scroll-stage selection and other reads are used on a Naga V2 Pro and BlackWidow Chroma V2. Current DPI, polling and top-level brightness setters require matching read-back; legacy BlackWidow brightness has no paired getter and is gated by default. The latest receive-frame checks passed mocks plus read-only BlackWidow and awake Naga getters; no device write was part of this final hardware pass. |
| Naga side plates | 🟢 solid | The mouse reports plate swaps; Neuron debounces them and scopes binds to the seated plate. Detaching clears that layer. |
| Trigger → action dispatch | 🟢 solid | Binds, HyperShift layers and app-focus rules use one tested engine. |
| Arm gate | 🟢 solid | The process starts disarmed, then a normal Windows GUI launch arms input when live dispatch starts so tray remaps work after logon. `--safe` and crash recovery stay disarmed. Tests cannot arm input; device writes and synthesized input have separate controls. |
| Audio control | 🟢 solid | Mute, gain and output switching use the OS mixer. Also tested with the BlackShark V2 and its included USB sound card, and the Seiren V3 Mini; these have no extra device-specific Neuron controls. |
| Synapse import, purge and discover | 🟢 solid | Plaintext export import, Windows purge and device discovery are implemented. Encrypted Synapse cloud profiles are not supported. |
| Notifications | 🟢 solid | Visual cards and optional audio confirm committed changes. |
| Profiles | 🟡 works, polishing | Capture, apply, rename and app-based switching are implemented. A profile groups settings, lighting and binds; a recent pass fixed lifecycle edges that need continued use. |
| Device adoption | 🟡 works, polishing | Capability probing synthesizes definitions for unfamiliar `razer_report` devices and direct-attached Logitech HID++ devices. The Naga V2 Pro and BlackWidow Chroma V2 are hardware-verified; HID++ adoption is read-only and has no hardware verification. |
| Lighting | 🟡 works, polishing | Firmware effects, per-key frames, pattern × spectrum layers, and live data layers are implemented. The newer layer editing and data feeds need more everyday use. |
| Macros and beacons | 🟡 works, polishing | BOUND and RAW CPython workers start on demand and then stay warm. Ask/notify, persistent state, macro composition and a source-preserving block editor are implemented. API documentation and long-run ergonomics need work. RAW Python is unsandboxed. |
| Main GUI | 🟡 works, polishing | The Slint window defaults to FemtoVG/OpenGL. The software UI renderer is compiled in and can be forced with `NEURON_RENDERER=software`. The opt-in WGPU UI renderer builds, but measured idle CPU and memory were higher on the development machine; it does not accelerate overlays or material shading. Windows overlay instruments still compose pixels on the CPU. |
| Reliability and recovery | 🟡 works, polishing | Flight recorder, crash log and read-only diagnostics are wired. Windows auto-relaunch is implemented but has not been exercised by a real crash or hang. |
| Onboard memory | 🟠 partial | Storage accounting and volatile writes work. Full onboard profile-slot persistence and scroll feel-curves are not complete. |
| Spellweaving at scale | 🟠 under-tested | Gesture recognition and radial dispatch work. Large glyph vaults and fully populated radial menus need sustained use. |
| Instruments | 🟠 uneven | Teleport, tether, whiteboard, glance, window actions, dial, knockback and control are present at different maturity levels. The whiteboard cannot save ink to disk yet. |
| CLI and headless daemon | 🟠 under-tested | The installed Windows CLI has driven real hardware and shares the GUI's core engine. Its broad command surface and daemon path have had less day-to-day use. |
| Protocol host | 🟠 early | Loopback Chroma REST and OpenRGB reach the lighting arbiter. Native Chroma shared memory uses an optional protected section broker with the regular tray at Limited integrity. A synthetic named-mapping test replays a captured game frame through the production snapshot and decode paths; live game compatibility still needs verification. Client counts are bounded; richer Chroma interpretation and dynamic redraw remain planned. |
| Momentary mic | 🟠 under-tested | Press holds mute and release restores it. Config swaps, worker respawn and exit release held state; the path has had limited real-world use. |
| Install and update | 🟡 works, polishing | The v0.1.0 Windows package was installed into a clean folder, checked for runtime DLLs, and used to drive hardware through the installed CLI. The current Inno package installed into a previously absent per-user app directory on the development machine; installed file hashes matched staging, its CLI listed attached devices, and its tray served a REST session. This is not a separate clean-machine run. The optional protected Chroma broker is packaged but requires a separate same-account administrator install; installer and updater preflight an old elevated tray task before replacing files. Linux update logic has synthetic install, rollback and checksum tests, but no released Linux package or native installation run. |
| Linux HID | 🟠 hardware-unverified | The hidraw transport builds and passes local tests under WSL2. No Razer device has exercised its feature-report path on Linux. |
| Linux GUI | 🟠 partial | The source builds a Slint window with device settings, lighting editor, GTK tray and best-effort hotkeys. Live input, audio and overlay work is on [`codex/linux-runtime-parity`](https://github.com/worflor/neuron/tree/codex/linux-runtime-parity). Its overlay does not yet match Windows, and its input path needs a native desktop and hardware run. v0.1.1 has no Linux download. |
| macOS | ⚪ planned | No backend or release build. |

For device-write evidence and feature gates, see the [README ledger](../README.md#honesty-proven-gated-absent). If a feature marked solid breaks, please [report the device and steps to reproduce](https://github.com/worflor/neuron/issues).

## Current engineering checks

On Windows, `./validate.ps1 -Mode full -Locked` passed on 2026-09-24 after the protected Chroma broker, startup and synthetic Chroma mapping changes. That pass included the workspace tests, strict Clippy, gated-write feature checks, optimized release build, and CI-safe ignored tests. `cargo check -p neuron-app --features wgpu-renderer --locked` also passed earlier. Physical read-only getters were checked separately on the BlackWidow and awake Naga; the suite does not verify every hardware write or exercise Linux and macOS runtime behavior.

A local Windows package smoke built the app, CLI and optional Chroma broker with the static C runtime and produced a ZIP and Inno installer. The `v0.1.1-audit2` Inno package installed into a previously absent per-user app directory on this development machine; the install log reported success, seven checked installed files matched staging by SHA-256, the installed CLI reported `neuron 0.1.1` and listed the keyboard, mouse and microphone. The installed tray started, served Chroma REST, and opened, heartbeated and closed a synthetic session. The development tray was restored afterward. Packaging now stages tracked docs and skills rather than copying ignored local raw Chroma captures. `SOURCE.txt` records a modified working tree. This was not a separate clean-machine run or a published release.

The idle multi-slot weave capture now waits for input instead of repeatedly polling. A safe live capture on the Windows development machine fell from about 310–320 capture polls per second to 17–18; that counter is not a whole-process CPU measurement. The separate single-phrase capture path still polls at 3 ms while awaiting a rhythm, including an active beacon ask; that is a remaining power-efficiency target, not a new behavior in this change. A later read-only sample of the old resident app measured 18.95 CPU seconds in 20 seconds, with 18.69 seconds on `neuron-live-dispatch`. Its Win32 wait watched the whole thread queue while `PeekMessageW` drained only one window; a pending thread or second-window message could therefore cause an immediate-wake loop. The queue drain has been corrected and a hardware-free test reproduces the Win32 mismatch. With normal input arming restored, a longer run exposed the same mismatch in the spellweave capture: `neuron-weave-presenter` used 19.2 CPU seconds in 20 seconds while its wait watched all thread messages but its drain read only one window. That wait now listens only for Raw Input, with a Windows test for an unrelated thread message.

After rebuilding, armed hidden-tray samples at 135 and 636 seconds of uptime measured 0.688 and 0.281 CPU seconds per 20 seconds on the 12-logical-processor machine. Private allocation stayed around 142 MB; Windows trimmed the working set from about 76 MB to 38 MB while a package build ran. The older README claim of about 14 MB was removed pending a comparable memory baseline. FemtoVG/OpenGL remains the default after the opt-in WGPU path used more idle CPU and memory on that machine. These observations do not establish Linux or macOS performance.

On the Windows development machine, the protected Program Files broker matched the packaged binary by SHA-256 after an update. All 14 global Chroma sections opened from a Limited process, and a separate read-only check confirmed the Limited tray wore the native arbitration mask. The live SYSTEM page reported native SDK and REST available; a REST session opened, read and closed. The tray's global open hotkey showed the window and closing it returned to the resident tray process. A read-only native snapshot attached to the live sections and found no active game frame. The synthetic named-mapping test replays a captured game frame without using the live namespace. No Chroma game was running for an end-to-end game frame check.

Profile lifecycle tests cover recovery after both interruption points of a staged sidecar delete and preserve conflicting files. Profile and bind loading stop when recovery fails; the GUI reports a broken profile row and the CLI reports an error. A concurrent CLI rename or delete between profile enumeration and parsing can briefly show a broken row in the GUI. This remains a consistency edge, not a reproduced data-loss case.

In an optimized synthetic gallery run on that machine, skipping unused legacy glass taps reduced the six-card 220×132 batch median from about 120 ms to 108 ms with the same pixel checksum. The gallery only animates while visible on the SYSTEM page and drops ticks when its worker is busy; this timing is still above its 100 ms target. The largest synthetic gesture vault case (64 signatures, 128 templates) measured a 4.9 ms median in an optimized build. Neither benchmark measures tray idle CPU.

The Razer 91-byte receive path now requires a full frame, matching transaction and command, valid CRC, and valid framing before using a reply. Mock tests cover truncated, damaged and mismatched replies. A read-only firmware getter on the attached BlackWidow Chroma V2 succeeded with the new validator. The Naga V2 Pro initially timed out on firmware, battery and DPI reads while inactive; the released v0.1.0 CLI also timed out in that state. After the mouse was woken, the installed current CLI read a valid `00/81` firmware reply, 2% battery and 800 × 800 DPI with the resident app stopped. No device write was made in this final hardware pass. The fast lighting stream invalidates its frame cache after a failed drain so the next tick resends it.

The Windows GUI tests run one window test per child process, because only the first window worked in a shared test process. The process-wide input gate stays disarmed in tests; pocket stress tests use an in-memory clipboard authorization instead. These are test and software checks, not proof of visible lighting or device behavior.
