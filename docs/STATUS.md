# neuron: state of the project

This page tracks the v0.1.4 Windows beta candidate: what has been exercised on hardware, what is implemented but needs more use, and what is still planned. The [README](../README.md) has the device-write ledger.

| grade | meaning |
|---|---|
| 🟢 solid | Daily-driven or directly tested on the named hardware. |
| 🟡 works, polishing | Usable, with recent changes or rough edges still being exercised. |
| 🟠 under-tested or partial | Implemented in part or not yet exercised enough to rely on broadly. |
| ⚪ planned | No working implementation yet. |

## Feature status

| area | grade | evidence and limits |
|---|---|---|
| Device control | 🟡 works, polishing | DPI, polling, brightness, battery, scroll-stage selection and other reads are used on a Naga V2 Pro and BlackWidow Chroma V2. DPI, polling, brightness and scroll-stage setters require matching read-back; the scroll-stage cycle reads the device's own stage and enabled count (`15/80`, `15/81`, verified live 2026-09-29). The legacy BlackWidow brightness getter and write/read round-trip were checked on the attached board. The latest receive-frame checks also passed mocks plus read-only BlackWidow and awake Naga getters. |
| Naga side plates | 🟢 solid | The mouse reports plate swaps; Neuron debounces them and scopes binds to the seated plate. Detaching clears that layer. |
| Trigger → action dispatch | 🟢 solid | Binds, HyperShift layers and app-focus rules use one tested engine. |
| Clipboard transforms, pockets, history and screenshots | 🟠 under-tested | Typed ordered text transforms can include one stored Python macro that receives the current intermediate text as `ctx.clipboard` and must return a string; macro-backed transforms run asynchronously behind the arm gate and use the clipboard sequence check before commit. Bounded regex previews, full-format named pockets, in-session displaced-state history, and screen/window/region screenshot actions are implemented. On Windows, native text transforms, four-format Pocket/history restore, image Pocket restore, window PNG/clipboard capture and region cancellation were exercised on 2026-10-01. Macro-backed transform behavior, region drag capture and broader application-format compatibility remain unverified. Headless CLI/daemon screen and window captures report completion to stderr; region selection requires the resident app. Durable pockets are capped at 128 MiB, history at 20 items / 16 MiB, transforms at 1 MiB of text, and explicit CLI body inspection at 16 MiB. |
| Lighting-layer, dial scroll, Undo | 🟠 under-tested | Typed layer mutations validate before the app persists and restreams the selected stack. Dial keeps output/mic compatibility and adds hover/hold-anchored Windows scrolling. The 20-entry session journal uses successful audio/profile receipts and app lighting receipts; the headless daemon has no compositor target. Automatic app-focus switches and first activation from an empty profile cursor are not undoable. The Windows inline layer editor and direct/nested output-gain Undo were exercised on 2026-10-01. Physical layer output, anchored window scrolling and microphone-gain Undo remain unverified. |
| Controllers and any HID device | 🟠 under-tested | Windows only. Buttons, sticks, triggers and hats come from each device's own report descriptor: the analog model learns whether an axis rests centred (stick) or at an end (trigger), holds that once established (a trigger pulled through a long race stays a trigger), and turns every direction into a bindable control. A stream whose buttons contradict its descriptor is caught and feeds neither binds nor the radial. Pads GameInput delivers (Xbox-protocol pads, and any other it classes as a gamepad) come through it, and Raw Input's copy of the same pad is dropped; everything else comes through Raw Input, and a descriptor-less stream through a layout file (Switch Pro, from SDL's zlib driver). A pad unplugged mid-press releases what it held. Only GameInput and layout pads share the standard-pad button names; a Raw Input pad's buttons are its descriptor's own numbers. A held cast trigger plus a pushed stick aims the radial, and the aiming pad renders the wheel as a knob (`knob.rs`): detent ridges at wedge boundaries scaled by deflection and sweep speed, a speed-sharpened click panned to the trigger motor on the stick's side, a double tap at a fan's rim, and a struck-then-settling fire; PAD FEEL on the radial sets its strength from off to 150%, and "feel it" plays the phrase on the pad in hand. Rumble is built from a Game Pad collection's declared HID Physical Interface Device outputs: the XInput-HID shadow every Xbox-protocol pad gets is verified (all four motors of a PowerA pad, at any strength, 2026-09-30; `neuron rumble --tour`), other pads' motors carry no declared roles and stay behind `NEURON_HAPTICS_WRITE`, and joystick and wheel force feedback is never written. GameInput's unit id is opaque, so rumble refuses two connected pads with the same VID:PID rather than guessing which shadow belongs to which pad. A pad cast trigger uses sticks matching its canonical PID; identical physical pads share that id, so the selected path is latched only once aiming engages and a disconnect cancels the cast. Battery and motion from GameInput, and any non-control value a HID descriptor declares (a Battery Strength field becomes a battery level), feed a sensor registry (`neuron pads`). A device's keyboard, pointer and HID collections are separate streams, so a click can't release a key held on the same device. Every device shows as its badge, an emblem and a name it reports or you give it (`badges.toml`). Verified 2026-09-30 on a PowerA pad: background reading, no events at rest, binds fire, the stick aims and fires the radial, the knob's feel. Not yet exercised: the unplug release, Bluetooth pads, two identical pads (identity is the USB pid alone, so they share one), the Switch Pro stream (its start-up answers but stays gated, `NEURON_PAD_INIT`), Linux and macOS sources. |
| Firmware-performed binds | 🟠 under-tested | On a device with firmware button functions (Naga V2 Pro thumb grid), a key bind is written into the mouse and other binds ride a private F-key the hook swallows, handed out from F24 down and never shared between devices; a software-injected F-key (a hotkey tool) is never taken as one, but a physical macro pad sending the same F-key while it is assigned would be. The Naga is kept in normal mode, where those functions run. Verified live 2026-09-30 on the 12-button plate over the cable (a firmware `g`, a host scroll-stage cycle, factory restore on exit). A button two plates bind differently is planned for the seated plate, re-planned when the plate changes (unit-tested; not yet verified live). Not yet exercised: the dongle link, sleep/wake re-apply, the 6-button plate, press-to-bind capture of a bound key. |
| Arm gate | 🟢 solid | The process starts disarmed, then a normal Windows GUI launch arms input when live dispatch starts so tray remaps work after logon and Windows crash recovery. `--safe` stays disarmed. Tests cannot arm input; device writes and synthesized input have separate controls. |
| Audio control | 🟢 solid | Mute, gain and output switching use the OS mixer. Also tested with the BlackShark V2 and its included USB sound card, and the Seiren V3 Mini; these have no extra device-specific Neuron controls. |
| Synapse import, purge and discover | 🟢 solid | Plaintext export import, Windows purge and device discovery are implemented. Encrypted Synapse cloud profiles are not supported; a Synapse 3 layout is read instead from the mapping log its service writes, which holds only what the last Synapse session set (keys and mouse buttons; macros, modifier chords and DKM-addressed buttons are reported, not imported). |
| Notifications | 🟢 solid | Visual cards and optional audio confirm committed changes. |
| Profiles | 🟡 works, polishing | Capture, apply, rename and app-based switching are implemented. A profile groups settings, lighting and binds; a recent pass fixed lifecycle edges that need continued use. |
| Device adoption | 🟡 works, polishing | Capability probing synthesizes definitions for unfamiliar `razer_report` devices and direct-attached Logitech HID++ devices. The Naga V2 Pro and BlackWidow Chroma V2 are hardware-verified; HID++ adoption is read-only and has no hardware verification. |
| Lighting | 🟡 works, polishing | Firmware effects, per-key frames, pattern × spectrum layers, and live data layers are implemented. Wildlife adds a deterministic seasonal cellular pattern and read-side key feedback; it has not yet been visually checked on real hardware. The newer layer editing and data feeds need more everyday use. |
| Macros and beacons | 🟡 works, polishing | BOUND and RAW CPython workers start on demand and then stay warm. Ask/notify, persistent state, macro composition and a source-preserving block editor are implemented. API documentation and long-run ergonomics need work. RAW Python is unsandboxed. |
| Main GUI | 🟡 works, polishing | The Slint window defaults to FemtoVG/OpenGL. The software UI renderer is compiled in and can be forced with `NEURON_RENDERER=software`. The opt-in WGPU UI renderer builds, but measured idle CPU and memory were higher on the development machine; it does not accelerate overlays or material shading. Windows overlay instruments still compose pixels on the CPU. |
| Reliability and recovery | 🟡 works, polishing | Flight recorder, crash log and read-only diagnostics are wired. Windows auto-relaunch is implemented but has not been exercised by a real crash or hang. |
| Onboard memory | 🟠 partial | Storage accounting and volatile writes work. Full onboard profile-slot persistence and scroll feel-curves are not complete. |
| Spellweaving at scale | 🟠 under-tested | Gesture recognition and radial dispatch work. Large glyph vaults and fully populated radial menus need sustained use. |
| Instruments | 🟠 uneven | Teleport, tether, whiteboard, glance, window actions, dial, knockback and control are present at different maturity levels. The whiteboard cannot save ink to disk yet. |
| CLI and headless daemon | 🟠 under-tested | The installed Windows CLI has driven real hardware and shares the GUI's core engine. Its broad command surface and daemon path have had less day-to-day use. |
| Protocol host | 🟠 early | Loopback Chroma REST and OpenRGB reach the lighting arbiter. Native Chroma shared memory uses the packaged protected section broker with the regular tray at Limited integrity. A synthetic named-mapping test replays a captured game frame through the production snapshot and decode paths, and the final installed build received live native Chroma traffic from a real game. Client counts are bounded. A Chroma lab under LIGHTING → VISITORS splits the connected game's own keyboard frames into an ambient colour, held key colours, animated keys and recurring effects with stable ids; that grouping is regression-tested against 750 frames of real Overwatch play and has been tuned on that one game only. Effect ids, names and hidden flags persist per game exe. From the lab an effect can be hidden (the keyboard holds the at-rest picture from the early guess, about 0.25 s in), and a lens can restyle all game paint (hue, saturation, brightness). An effect can also be bound to a feedback action through a game-light trigger on the one dispatch engine, which refuses any rule that would press keys, click, run a macro or a command. A Game Light data layer carries the game's ambient and effect colours to any device. The frame codec reads each device class (keyboard, mouse, headset, mousepad, keypad, room lights) at its own record layout, checked against a live Overwatch capture and an independent open-source reader. It decodes custom grids, per-key overrides and static colours, and renders the SDK's parametric effects (wave, spectrum, breathing, blinking) rather than reading them as colour; a suspended game reads as suspended. The lab keeps the resting pictures a game returns to as named scenes. A scene can notify when it ends while the game isn't focused, and can bind a feedback action to its start. A capture saves as both the fixture stream and a `.chroma` animation in the SDK's file layout; no Razer tool has opened one yet. Against a running Overwatch, the lab showed the mouse, headset, mousepad and room grids, recognised a saved scene under the same id after a restart, and saved a scene's name, alert flag and bound action. A scene alert firing, a bound action running, hiding, the lens and the Game Light layer have not been exercised live in a match; the lab's live tap has no automated tests. The non-keyboard layouts are verified only on static frames, and parametric effects only on synthetic records. Broader game compatibility remains planned. |
| Momentary mic | 🟠 under-tested | Press holds mute and release restores it. Config swaps, worker respawn and exit release held state; the path has had limited real-world use. |
| Install and update | 🟡 works, polishing | The current Windows package was installed from a clean application state, updated over a running tray, reapplied through the portable updater, and cleanly uninstalled on the development machine. Installed file hashes matched staging; uninstall removed the binaries, startup tasks and protected broker while preserving generated user configuration. Setup provisions or refreshes the protected Chroma broker after UAC approval and migrates the historical elevated tray task to a limited task; the standalone updater refuses that unsafe historical task before changing files. The machine-wide broker and startup task support one owning Windows user. This is not a separate clean-machine run. Linux update logic has synthetic install, rollback and checksum tests, but no released Linux package or native installation run. |
| Linux HID | 🟠 hardware-unverified | The hidraw transport builds and passes local tests under WSL2. No Razer device has exercised its feature-report path on Linux. |
| Linux GUI | 🟠 partial | The source builds a Slint window with device settings, lighting editor, GTK tray and best-effort hotkeys. Live input, audio and overlay work is on [`codex/linux-runtime-parity`](https://github.com/worflor/neuron/tree/codex/linux-runtime-parity). Its overlay does not yet match Windows, and its input path needs a native desktop and hardware run. No Linux download is published yet. |
| macOS | ⚪ planned | No backend or release build. |

For device-write evidence and feature gates, see the [README ledger](../README.md#honesty-proven-gated-absent). If a feature marked solid breaks, please [report the device and steps to reproduce](https://github.com/worflor/neuron/issues).

## Current engineering checks

On Windows on 2026-10-03, `./validate.ps1 -Mode full -Locked` passed for the v0.1.4 candidate: 1,179 core tests, 261 app tests and 239 host tests, plus integration tests, strict Clippy, gated-write feature checks, an optimized release build and the CI-safe ignored tests. Disarmed software-renderer screenshots checked the controller editor and lighting page. The Wildlife promotional mock uses frames from the actual compositor and the existing 6×22 key map, rendered with Cycles OptiX on an RTX 3060; it does not establish physical LED behavior. No new Linux, Tartarus or Switch Pro hardware run was performed.

On Windows on 2026-10-01, the isolated review app exercised DIRECT filtering, eight-row pagination, editing a filtered binding without changing its neighbours, and reopening saved clipboard and lighting actions. A native clipboard sequence restored a four-format sample, transformed it to `ORDER [7391] SHIPPED`, and restored the original full-format input from session history. A window screenshot produced a PNG and a clipboard image; an image Pocket restored and retained its 4,215,260-byte payload. Region selection opened and cancelled without creating a file; automated dragging shifted focus and cancelled the selector, so completed region capture is not verified. Direct output gain changed the Razer USB sound card from 26% to 27%, Undo restored 26%, and a nested gain/Undo sequence also restored 26%. All nine read-only SYSTEM probes passed, including BlackWidow Chroma V2 firmware and the Seiren V3 Mini endpoint. Review bindings, Pocket contents and history were removed, and the original empty clipboard and output gain were restored. Wildlife was checked in the software preview; its physical LED output and the revised controller casting under live stick movement still need owner testing.

On Windows, `./validate.ps1 -Mode full -Locked` passed on 2026-10-01 after the action-depth integration. It ran 1,146 core tests, 261 app tests and 239 host tests, plus strict Clippy, gated-write feature checks, an optimized release build, and the CI-safe ignored tests. `cargo check -p neuron-app --features wgpu-renderer --locked` also passed earlier. Physical getters were checked separately on the BlackWidow and awake Naga; the suite does not verify every hardware write or exercise macOS runtime behavior.

Under WSL2 Ubuntu 24.04, `pwsh ./validate.ps1 -Mode full -Locked` passed on 2026-09-29 for the same candidate. It ran 953 core tests, 227 app tests and 232 host tests, including the Linux app and hidraw transport, then passed strict Clippy, the gated-write feature matrix, an optimized release build and the CI-safe ignored tests. This proves the Linux source build and platform-free behavior in WSL2; it is not a native desktop, tray, input or hardware run.

The v0.1.3 candidate built the same three static-runtime executables and produced a portable ZIP and Inno installer locally. Its staged CLI reported `neuron 0.1.3` and listed the attached BlackWidow, Seiren and Naga. The locally compiled candidate installer was not installed then. On 2026-10-03, the published v0.1.3 installer passed the updater's checksum and GitHub provenance checks and updated the development machine. All three installed executables match the verified published ZIP by SHA-256, and 17 backed-up configuration files remain byte-identical. The installed CLI and SOURCE record both report v0.1.3; the running tray and enabled Limited startup task both use the installer-managed path. The updater reports up-to-date, and user configuration remains outside the installed payload.

The v0.1.2 candidate built three static-runtime Windows executables and produced a portable ZIP and Inno installer locally. Its staged CLI reported `neuron 0.1.2` and listed the attached BlackWidow, Seiren and Naga. Every installed executable matched staging by SHA-256. Setup provisioned a changed protected broker before its first app-file write; declining that UAC path left the app payload unchanged. A healthy repeat install required no second prompt, stopped and restarted a running tray, and retained a Limited startup task. A protected pending ownership record was also recovered into the final receipt. Installer-managed update, portable update, a clean application-state install, and uninstall completed successfully; the portable update preserved an unshipped user-state probe and its marker. Uninstall removed every shipped file, both user startup task names, the SYSTEM broker task and its protected directory while preserving generated configuration. This is not a separate clean-machine or live-game run.

The idle multi-slot weave capture now waits for input instead of repeatedly polling. A safe live capture on the Windows development machine fell from about 310–320 capture polls per second to 17–18; that counter is not a whole-process CPU measurement. The separate single-phrase capture path still polls at 3 ms while awaiting a rhythm, including an active beacon ask; that is a remaining power-efficiency target, not a new behavior in this change. A later read-only sample of the old resident app measured 18.95 CPU seconds in 20 seconds, with 18.69 seconds on `neuron-live-dispatch`. Its Win32 wait watched the whole thread queue while `PeekMessageW` drained only one window; a pending thread or second-window message could therefore cause an immediate-wake loop. The queue drain has been corrected and a hardware-free test reproduces the Win32 mismatch. With normal input arming restored, a longer run exposed the same mismatch in the spellweave capture: `neuron-weave-presenter` used 19.2 CPU seconds in 20 seconds while its wait watched all thread messages but its drain read only one window. That wait now listens only for Raw Input, with a Windows test for an unrelated thread message.

After rebuilding, armed hidden-tray samples at 135 and 636 seconds of uptime measured 0.688 and 0.281 CPU seconds per 20 seconds on the 12-logical-processor machine. The final installed app's resident budget lane then measured 0.195% and 0.208% of total CPU in two 30-second idle windows. Private allocation moved from 148,910,080 to 148,807,680 bytes, handles from 543 to 541, threads from 41 to 38, and both windows wrote zero bytes. The older README claim of about 14 MB was removed pending a comparable memory baseline. FemtoVG/OpenGL remains the default after the opt-in WGPU path used more idle CPU and memory on that machine. These observations do not establish Linux or macOS performance.

On the Windows development machine, the protected Program Files broker and ownership receipt matched the packaged binary after install, update, and interrupted-transaction recovery. All 14 global Chroma sections opened from a Limited process, and a separate read-only check confirmed the Limited tray wore the native arbitration mask. A live REST client initialized a session, read it, heartbeated, stored and applied an effect, freed it, and closed the session; every result was success. Opening the installed app surfaced the existing tray process, and closing the window returned it to hidden resident state. A read-only native snapshot attached to the live sections while no game was active, and the owner later verified the final installed build with a live Chroma game. The synthetic named-mapping test continues to cover a captured frame without using the live namespace.

Profile lifecycle tests cover recovery after both interruption points of a staged sidecar delete and preserve conflicting files. Profile and bind loading stop when recovery fails; the GUI reports a broken profile row and the CLI reports an error. A concurrent CLI rename or delete between profile enumeration and parsing can briefly show a broken row in the GUI. This remains a consistency edge, not a reproduced data-loss case.

In an optimized synthetic gallery run on that machine, skipping unused legacy glass taps reduced the six-card 220×132 batch median from about 120 ms to 108 ms with the same pixel checksum. The gallery only animates while visible on the SYSTEM page and drops ticks when its worker is busy; this timing is still above its 100 ms target. The largest synthetic gesture vault case (64 signatures, 128 templates) measured a 4.9 ms median in an optimized build. Neither benchmark measures tray idle CPU.

The Razer 91-byte receive path now requires a full frame, matching transaction and command, valid CRC, and valid framing before using a reply. Mock tests cover truncated, damaged and mismatched replies. A read-only firmware getter on the attached BlackWidow Chroma V2 succeeded with the new validator. The Naga V2 Pro initially timed out on firmware, battery and DPI reads while inactive; the released v0.1.0 CLI also timed out in that state. After the mouse was woken, the installed current CLI read a valid `00/81` firmware reply, battery and 800 × 800 DPI with the resident app stopped. The final packaged CLI read the BlackWidow's legacy `03/83` brightness getter at 40%, wrote and verified 41%, then restored and verified 40%. The fast lighting stream invalidates its frame cache after a failed drain so the next tick resends it.

The Windows GUI tests run one window test per child process, because only the first window worked in a shared test process. The process-wide input gate stays disarmed in tests; pocket stress tests use an in-memory clipboard authorization instead. These are test and software checks, not proof of visible lighting or device behavior.
