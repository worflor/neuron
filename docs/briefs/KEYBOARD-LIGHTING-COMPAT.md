Status: §1 and the Razer half of §3 step 1 are built (2026-11-16); the durable parts are in
`docs/TDD.md` §5.8, the ledger (`razer/tx/keyboard-cohorts`, `razer/enum/synth-lighting-blocks`)
and `protocol/razer-keyboards.toml`. Not yet checked on a V3 or V4 X. §2 (other vendors,
LampArray) is research only. Grades below are source agreement only.

Built: tx-cohort retry of the backlight read, LED and matrix size from the atlas (LED probed where

lighting overrides and driver mode, `neuron compat lighting`, a firmware model and a keyboard

interface pins, a heal that could pass on a board already showing a frame, txs moving each other

lost on rewrite, stale-buffer misreads in the probe, the keyboard path on mats and docks, and a

third source, values ranked by independent lineage, the atlas regenerated by a testkit tool
(`razer-atlas`) instead of scratch scripts, every OpenRGB detector collection kept (the V4's moved
at firmware 1.5), openrazer's per-PID reply wait as the write pacing of a keyboard PID, and
settling for every board with a scene, not only the selected one.

Open:
- The LampArray write tier and a native-vs-compatibility indicator (no LampArray device on the
  desk; the V4 X has one).
- A typed per-field provenance table in generated files (today: comment lines plus the settle
  record), and a `LightingFamily` seam so HID++ and LampArray lighting plug into settling.
- `path_instance` groups each Windows collection as its own unit app-wide; compatibility code uses
  `transport::unit_key` instead. Fixing the app-wide identity is the owner's call.
- Learned legacy keyboards' brightness block writes VARSTORE ([0x01, 0x05], as the Chroma V2's
  live-verified block does) and `capability::set_brightness` ignores `Store` on that path.
- Frame rows are not read back. A board that never answers rows (openrazer's "no GET after rows"
  V4 family) now still latches each frame, resending it whole; skipping the reply read entirely
  for that family is untested on hardware. A `0F/80` region getter; confirming `AmbientLightingEnabled` is the
  "Use Dynamic Lighting on my devices" switch.

## 1. Why the BlackWidow V3 (#33) and V4 X (#23) stay dark

**What the V3 user saw** on 0.1.7 and 0.1.8: the profile reports `DEGRADED · brightness: … no
connected device supports SetBrightness`. That means the synthesized def has no brightness write.
`matrix_lighting` emits one only when the `0F/84` getter answered (`synth.rs` `brightness_proven`),
so on the V3 that getter never answered.

Ranked causes. Each is a code fact checked against openrazer `razerkbd_driver.c`:

1. **Transaction id.** The probe sends every getter at `PROBE_TX = 0x1F`, and
   `razer_reply_status` drops any reply whose `b[2]` differs from the request's tx.
   - openrazer reads V3 brightness with `0F/84 [VARSTORE, 0x05]` at **tx 0x3F** (L4375-4382). The
     same 0x3F cohort covers BW V3 / V3 TK / V3 Pro wired, Huntsman (v1, Elite, TE, Mini),
     Cynosa (v1, Pro, Lite), DeathStalker V2, and BW Lite/2019/Essential.
   - The note "getters ignore tx" was proven only on the Naga and the Chroma V2. It does not hold
     for every board.
   - Fix shape: probe the lighting getters at 0x1F, then 0x3F, then 0x9F (HyperSpeed dongles).
     Record the tx that answered as the def's lighting tx. That turns tx from `Heuristic` into
     `Proven` for lighting.
2. **LED id on keyboard effects.** Synthesized keyboards send effects and frame activation on
   LED 0x00.
   - openrazer and OpenRGB both use BACKLIGHT_LED **0x05** for V3/V4 effects and brightness. The
     one exception is OpenRGB's DeathStalker V2 Pro, which uses 0x00.
   - Only the custom-frame activation `0F/02 [00, 00, 08]` carries 0 / 0.
   - The 4642879 commit's reading of Synapse's RzCtl modules (LED 0x00) disagrees with both
     projects. Treat 0x05 as the agreed value for effects and keep 0x00 for activation.
3. **Pipe selection.** The Razer dialect claims any VID 0x1532 collection with a 91-byte feature
   report (`dialect.rs:215`). Adoption keeps the first one that answers the firmware getter
   (`synth.rs:1069`). openrazer addresses each family at a specific USB interface (wIndex), and
   OpenRGB opens a specific (interface, usage page, usage):

   | board | openrazer | OpenRGB |
   |---|---|---|
   | V3 (024E) | interface 3 | MI 3, **page 0x0C usage 0x01** (OpenRGB `18b0a15e`, fixing "V3 keeps cycling colours", GitLab #1890) |
   | V4 X (0293) | interface 2 | MI 2, 0x01/0x02 |
   | V4 / V4 Pro | — | moved 0x01/0x00 → 0x0C/0x01 at firmware 1.5 |

   The Chroma V2 answers on more than one interface; newer boards may answer identity getters on a
   pipe that ignores lighting. This is the only listed cause that fits the V4 X. Its tx 0x1F,
   class 0x0F and LED 0x05 all match what neuron would send, except the LED.
4. **Dynamic Lighting.** The V4 X descriptor fixture (`testdata/hid/0293-linux.json`) shows a
   LampArray on interface 3.
   - G HUB and Synapse 4 both refuse to drive lighting while Windows Dynamic Lighting owns the
     device.
   - No source shows Razer firmware rejecting `razer_report` writes while it is on. Untested.
5. **Stale auto file.** `is_stale_auto_def` retires only a v1 file shaped as 6×22 matrix on
   LED 0x04. A v1 file with no lighting, or with legacy-shaped lighting, survives forever. A
   lighting-relevant `SYNTH_VERSION` bump should retire any v1 keyboard file, not one shape.

**Desk test that settles 1–4 without a V3.** On the Chroma V2 and the Naga, toggle Dynamic
Lighting, write static, and read back. For the V3 and V4 X, ask the reporters for:

- `neuron diag` / Compatibility Lab output listing every 91-byte collection (interface, page,
  usage);
- which collections answer `0F/84 [00,05]` at 0x1F and at 0x3F (read-only).

Disagreements stay candidates, not facts:

- tx on Huntsman V2 / V3 Pro and DeathStalker V2;
- matrix size on V4 75% and V2 Analog.

What holds across all of these:

- The 0x3F vs 0x1F split is a firmware cohort (2018–21 vs 2021+), not a rule; openrazer PR #2151
  found no single rule.
- NOSTORE works everywhere in OpenRGB.
- Neither project needs driver mode for keyboard lighting.
- OpenRGB discovers regions by asking (`0F/80` regions, `0F/81` effects per region). That is a
  getter synthesis could add to the catalog.

Smaller points:

- **No GET after rows.** V4 / V4 Pro / V4 75% firmware dislikes a GET_REPORT after frame rows.
  That conflicts with neuron's rule that streaming writes check replies, so it needs a per-def
  "rows are fire-only" flag and a ledger note.
- **Underglow and wrist rest** are extra matrix rows (8×23, 9×22), not separate LED ids.
- **HyperSpeed dongles** carry their own PID, tx 0x9F and a ~4.9 ms wait, often on a different
  interface than the wired PID.

### LampArray specifics (Microsoft Learn, OpenRGB `HIDLampArrayController`)

- Win32 `CreateFile`/`HidD_*` can open the 0x59 TLC: it is not in Windows' system-opened table.
  WinRT `HidDevice` blocks it.
- The WinRT `LampArray` API works from Win32, but only applies state while the app is focused.
  Background ("ambient") control needs package identity (sparse MSIX) and the lighting
  AppExtension. Raw HID sidesteps that, and also sidesteps Windows' arbitration.
- Shipping evidence:
  - Logitech LIGHTSYNC (partner page);
  - HP / HyperX, ASUS laptops and MSI boards (OpenRGB issues);
  - QMK only as an open PoC (#22296);
  - Razer: no device list.

### Vendor SDKs (Chroma, GameSense, LGS/G HUB, iCUE, Aura)

They need the app neuron replaces, carry no read-back, and come with vague licences. Leave them
last or skip them.

**OpenRGB as a client.** It has the broadest coverage, with no hardware ack before protocol v6. It
must refuse to connect to neuron's own 6742 listener.

### Coexistence

No vendor app opens these devices exclusively. Each re-asserts its state, so the failure is a
silent fight. Detecting the vendor service, as neuron already does for Synapse, is the honest
answer.

## 3. Proposed order

1. **Razer V3 / V4 X** (device writes: owner sign-off; `risky`):
   - tx-probed lighting getters;
   - LED 0x05 for keyboard effects and brightness;
   - pipe chosen by which collection answers the lighting getter, not the firmware getter;
   - wider stale-file retirement;
   - a `0F/80` region getter in the catalog;
   - ledger entries for each.
   - Then ask both reporters to retest.
2. **LampArray dialect** over raw HID. The device supplies the layout, and the spec is the
   evidence. It needs a Dynamic Lighting coexistence test on the desk first.
3. **Logitech lighting** on the existing HID++ dialect. Issue #2 (hardware verification) gates it.
4. **QMK VIA / VialRGB**, with save and reset opcodes refused at the ledger level.
5. ASUS, SteelSeries, Corsair as owners of that hardware turn up with captures.

Open questions to settle on hardware:

- Does Dynamic Lighting ON change how Razer firmware treats `razer_report` writes?
- Do raw 0x59 writes and an active Dynamic Lighting controller fight?
- Do Logitech's `&LAMPARRAY` child devices open raw?
- Do EVision custom-colour writes hit flash?
- Read the SignalRGB plugin bytes, which were rate-limited this pass. They would lift ASUS and
  Logitech legacy from single-source to agreed.
